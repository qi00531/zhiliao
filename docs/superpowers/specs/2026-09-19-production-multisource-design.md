# 知了生产级多信源与知识沉淀设计

日期：2026-09-19  
状态：已确认设计，尚未进入实施计划

## 1. 产品目标

知了在用户明确授权的范围内持续发现多信源的新变化，筛选真正重要的信息，保留可验证证据，并将长期有价值的内容沉淀为可复用的个人知识。

产品不追求搬运全部信息或生成更多内容。没有重要变化时允许保持安静；AI 的职责是压缩、组织和回答，而不是增加认知负担。

## 2. 核心原则

- 采集、授权校验、增量识别、去重和游标管理全部由确定性规则代码完成。
- AI 不接触账号密码、Cookie、客户端数据库或平台底层接口。
- 内容经过连接器标准化并满足用户授权后，才可进入 AI 层。
- 读取授权、AI 处理授权和知识沉淀授权相互独立。
- 所有摘要、知识和变化都必须能够回到原始来源或证据。
- 用户可以撤销授权、停止同步、删除数据并导出知识。
- 平台抓取失败不等于没有更新；失败时保留原游标和明确失败状态。
- 优先采用官方 API、Webhook、RSS、IMAP；其次采用用户主动分享、浏览器扩展和文件导入；实验性采集只能作为可替换、可停止的连接器。

## 3. 统一数据流

```text
信源
→ 确定性连接器
→ Source
→ Document
→ Event
→ Change
→ Evidence
→ 用户授权边界
→ AI 摘要、分类与关联
→ 今日信息 / 知识库 / 行动
```

- `Source`：仓库、邮箱、会话、公众号或创作者等信源。
- `Document`：文章、邮件、消息、视频、对话等原始内容。
- `Event`：一次真实发生的更新事件。
- `Change`：与上次可靠状态相比发生的变化。
- `Evidence`：支撑事件与变化的链接、原文位置或快照。

同一变化即使从 GitHub、RSS 和官网重复发现，也只生成一个事件，同时保留多个证据。

## 4. 权限模型

每个私有信源分别管理三项权限：

1. 读取：知了可以接收该信源的新内容。
2. AI 处理：授权内容可以交给 AI 分析。
3. 知识沉淀：处理结果可以长期进入知识库。

撤销读取后立即停止新增同步。已导入历史是否删除，由用户单独决定，避免误删已经形成的知识。

## 5. 连接器边界

每个平台实现独立连接器，易变逻辑不得进入知识库、事件或 UI 核心。公共能力至少包括：

```text
resolveSource(input)
scanChanges(cursor)
normalizeDocument(raw)
checkConnectorHealth()
```

固定创作者类平台进一步提供：

```text
resolveCreator(profileUrl)
listRecentPosts(creatorId, cursor)
getPostMetadata(postId)
```

连接器状态包括：正常、等待授权、登录失效、平台限流、数据结构变化、游标异常、可能漏取和已暂停。设置页显示最近成功同步、最近发现内容、抓取频率、连接器版本和用户待处理事项。

## 6. 各信源设计

### 6.1 个人微信

- 第一阶段优先验证 Windows 微信桌面端。
- 用户逐个授权可读取会话，不默认读取整个微信。
- 文件变化只作为扫描触发信号；新增消息由消息 ID、会话 ID、时间和游标确定。
- 对微信数据目录只读访问，优先复制数据库及相关日志的快照，再在知了目录解析。
- 未授权会话内容不持久化、不展示、不发送给 AI。
- 不修改消息、未读状态或微信文件；不使用注入、Hook 或模拟协议登录。
- 产品以“知了上次成功同步后新增”为主，不将“微信未读”作为第一版可靠语义。

正式开发前必须验证数据库结构、加密状态、会话 ID 稳定性、版本兼容和操作系统只读权限。

### 6.2 飞书与钉钉

- 第一阶段只接入用户和组织明确授权的群聊。
- 不读取私人单聊、未授权群聊或组织全部消息。
- 优先使用官方应用、事件订阅、机器人和 API。
- 第一版仅接收授权后的新消息，不补抓历史聊天记录。
- 用户能够查看授权群聊、连接状态、最近同步时间、附件权限、AI 权限、停止接入和删除历史入口。

### 6.3 GitHub

- 使用 GitHub App 或 OAuth。
- 有管理权限的仓库优先使用 Webhook；其他关注仓库使用 API 自适应轮询。
- 关注 Release、PR、Issue、Commit 和文档变化。
- 保存仓库、对象 ID、更新时间和内容哈希，并与 RSS、官网事件去重。

### 6.4 RSS、官网、更新日志与文档

- 优先 RSS/Atom，并利用 ETag、Last-Modified 降低请求。
- 无 RSS 时才进行网页变化检测。
- 默认自适应频率，用户在统一设置中选择自动、更及时、更节制或暂停。
- 同一天相同事件合并，历史变化默认折叠，同时保留全部来源。

### 6.5 邮箱

- Gmail 使用 OAuth 只读、邮箱变化通知、历史游标和周期性补偿同步。
- Outlook/Microsoft 365 使用 Microsoft Graph。
- 通用邮箱使用 OAuth 或应用专用密码配合 IMAP 只读。
- 无法连接时允许用户将选定邮件自动转发到知了专属地址。
- 支持按文件夹、标签和发件人授权，并排除验证码、账单等敏感类别。
- 知了不得修改已读状态、移动、删除、回复或发送邮件。

### 6.6 微信公众号

区分用户已经收到的推送和主动监控公众号列表。

- 已收到推送：由个人微信授权连接器识别公众号、标题、文章链接和时间，再交给网页连接器获取公开文章。
- 主动监控：优先由用户转发文章或公众号建立关注；没有面向普通读者的稳定官方接口时，只能使用可替换、可停止的实验连接器。
- 实验连接器不得要求上传微信密码或 Cookie，不绕过验证码、访问限制或平台风控。

### 6.7 通用大模型聊天记录

每个客户端独立审计本地文件、数据库、IndexedDB 和缓存，验证完整落盘、稳定会话 ID、增量识别、令牌暴露和版本失效检测，不能因为存在本地目录就承诺聊天完整。

接入优先级：

1. 经验证完整稳定的本地数据只读解析。
2. 浏览器扩展主动保存当前会话。
3. 官方导出文件导入。
4. 用户复制或上传。
5. 网络请求截获只作为研究手段。

知了可以发现新增对话，但默认不沉淀全部试错过程。用户确认后才保留最终结论、关键依据、可复用方法和原始对话证据。

### 6.8 小红书与抖音

目标是持续监控用户指定的固定创作者，不做广泛搜索或批量下载。

第一版只保存平台、创作者 ID、作品 ID、标题或文案、发布时间、封面、原始链接和同步游标。默认不抓全量评论，不点赞、评论、关注，不访问私人内容，不绕过验证码和账号限制。

接入顺序为官方开放能力、公开主页低频检查、用户本机已登录浏览器；桌面客户端网络请求抓取仅用于技术验证。

开源项目只作为研究样本：`MediaCrawler` 因非商业许可证不得进入生产代码；`xiaohongshu-cli`、`ReaJason/xhs`、`Douyin_TikTok_Download_API` 和 `TikTokDownload` 用于研究页面状态、数据模型、作品列表、错误分类与服务化边界。生产连接器重新实现最小只读能力。

### 6.9 B站

- 低频监控用户指定 UP 主的公开投稿更新。
- 保存 UP 主 ID、BV 号、标题、简介、发布时间、封面、分区和原始链接。
- 使用 BV 号增量去重。
- 默认不下载视频，不采集评论弹幕，不读取付费或私人内容。
- 遇到限流、验证码、权限或接口变化时暂停。
- 开源工具、官方开放 API 和公开内容分别评估，不能因为存在开源项目就推定可以任意采集。

## 7. 抓取频率与可靠性

默认采用自适应频率，依据历史更新规律、最近更新时间、连续无更新次数、限流状态和用户关注程度调整。用户只选择自动、更及时、更节制或暂停，不暴露复杂的分钟级配置。

每次同步记录游标、原始对象 ID、连接器版本、成功时间和失败原因。检测到未知数据结构时必须停止解析，不得猜测字段或推进游标。

## 8. 首页与证据呈现

- 首页只强调当前真正需要注意的信息。
- 同一天相同事件合并并展示全部来源。
- 历史变化默认折叠。
- “查看证据”和“查看来源”使用同一个来源查看器。
- 单条证据直接打开精确位置；多个来源先展示来源列表。
- 来源查看器提供高亮原文、完整上下文、原始入口和抓取时间。
- 抓取频率、信源、权限和连接状态集中在设置中。

## 9. 知识库

知识库以主题聚合认知，而不是堆积文件。新内容首先作为独立来源文档保存，同类内容再聚合到主题下。

```text
主题
├── 当前摘要
├── 已确认知识
├── 可复用经验
├── 关联主题
├── 历史变化
└── 来源文档
```

- 每个主题只维护一份当前摘要。
- 新内容更新主题摘要或形成修订记录，不生成多份重复 AI 文档。
- 来源可以在主题页内展开，也可以独立查看。
- 支持“支持、补充、冲突、更新、来源于、应用于”等关系以及类似 Obsidian 的关系树。
- 问知识库时按需生成简短回答并附可点击来源，回答不自动写回知识库。
- 知识应支持导出和迁移，不锁定在知了内部。

## 10. AI 输出边界

AI 默认只提供一份摘要、重要性判断、主题归属、与已有知识的关系，以及必要时的一项行动建议。禁止默认生成多版本摘要、冗长解读、自动扩写或无来源推测。

## 11. 端侧顺序

- 当前优先完善电脑端多信源获取、证据、筛选和知识沉淀。
- 移动端后续承担快速接入、提醒和消费。
- 语音主要放在移动端，由用户设置每日状态，支持信息播报和追问，但不默认持续监听，也不承担底层抓取。

## 12. 产品依赖顺序

第一层是稳定标准信源：GitHub、RSS/Atom、官网与更新日志、邮箱、飞书和钉钉授权群聊。

第二层是本地授权信息：个人微信授权会话、微信公众号消息、大模型本地聊天记录。

第三层是易变平台连接器：小红书固定创作者、抖音固定创作者、B站固定 UP 主。第三层必须独立、可替换、可暂停，不能阻塞主系统。

## 13. 异常处理与验证要求

- 连接器必须区分无更新、访问失败、登录失效、限流、数据结构变化和权限撤销。
- 重试不得推进游标，不得重复生成事件。
- 未授权内容不得进入持久化、索引和 AI 请求。
- 只读连接器必须通过权限限制、快照读取、查询白名单和文件访问审计验证没有修改源数据。
- 每个连接器都需要契约测试、固定样本解析测试、增量去重测试、权限过滤测试和失效演练。
- 上线前重新核查平台官方能力、条款、许可证和商业使用边界。

## 14. 尚未确定

以下问题保留到对应子系统设计时决定：

1. B站字幕可合法取得时是否自动提取并摘要。
2. 小红书、抖音第一版是否接受必须登录本机浏览器。
3. 第一批支持哪些大模型客户端。
4. 微信本地数据库的实际可行性和版本范围。
5. 私有原始信息的保存期限、加密和删除策略。
6. AI 确认采用逐条、按信源还是规则自动放行。
7. 显式目标与根据使用行为推断兴趣的关系。
8. 知识冲突时如何更新当前认知。
9. 哪些连接器允许云端运行，哪些必须仅在本机运行。

## 15. 非目标

- 本文不构成实施计划或排期。
- 本阶段不实现任何生产连接器。
- 不以大规模采集、批量下载或绕过平台限制为产品能力。
- 不以生成更多内容作为产品价值。
